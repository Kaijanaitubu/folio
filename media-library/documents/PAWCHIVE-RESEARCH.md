# F-020：pawchiveインポーター実現性調査

現在の状態：調査後、投稿メタデータのみを実装した。[実装仕様](PAWCHIVE-SPEC.md)。以下は実装前の調査記録であり、元投稿リンク・Favoritesは引き続き未実装。

調査日：2026-10-14。対象はロードマップF-020のタイトル・作者・表紙・タグ、元FANBOX／Patreon投稿の副リンク、お気に入り投稿の一括取込。今回の作業は調査と資料作成のみ。アプリ・個人DB・サイトのアカウントには変更を加えていない。

## 結論

**個別投稿のメタデータ取得には具体的な実装の見込みがある。** サイト自身が案内する公開APIと、ログインなしの実応答を確認した。FANBOX・Patreonの投稿取得、作者名、画像URLの材料、タグ付き投稿を確認できた。既存Folioへの組み込みはまだ行っていない。

**お気に入り用APIも文書化されているが、実アカウントでの取得は未確認。** 公開仕様の認証はPawchiveのログインセッションCookieであり、nhentaiの専用APIキーと同じ方式とは確認できていない。キーを渡せば直ちにFavoritesを取得できるとは現時点では約束しない。

## 公開APIの確認

サイトのフッターのAPIリンクは [API入口](https://pawchive.pw/api/schema) → [サイト自身のSwagger資料](https://pawchive.pw/api/swagger_schema) に進む。Swaggerページ内にOpenAPI 3.0.1の仕様が埋め込まれている。公開ページのHTMLから仕様を読み、スクリプトを実行せず確認した。

APIの基点：`https://pawchive.pw/api/v1`。

| 目的 | GET経路 | 確認状態 |
|---|---|---|
| 個別投稿 | `/{service}/user/{creator_id}/post/{post_id}` | FANBOX・Patreonとも未認証でHTTP 200を確認 |
| 作者名・公開名 | `/{service}/user/{creator_id}/profile` | 両サービスでHTTP 200を確認 |
| 投稿一覧 | `/posts?o=0`、`/{service}/user/{creator_id}?o=0` | それぞれ50件の応答を確認。全件取得はしていない |
| 作者に属するタグ一覧 | `/{service}/user/{creator_id}/tags` | 資料に記載あり。作品ごとのタグの代わりには使わない |
| お気に入り一覧 | `/account/favorites?type=post` | 資料に記載あり。未認証リクエストでHTTP 401を確認 |

経路の存在・匿名取得の成功と、認証したお気に入り全件取得の成功を区別する。お気に入りの追加・削除API、Pawchiveへのコンテンツ投稿・転載機能はFolioの今回の対象に含めない。

## 実応答の調査記録

公開サンプルとして [FANBOX投稿API](https://pawchive.pw/api/v1/fanbox/user/6570768/post/1836570) と、その作者profileを取得した。Patreonは公開の最近の投稿一覧から一件を選び、[投稿API](https://pawchive.pw/api/v1/patreon/user/211857851/post/172312247)・profile・投稿HTMLを確認した。これはユーザーの個人アカウントやFavoritesではない。

- 投稿APIはJSONオブジェクトで、`id`、`user`、`service`、`title`、`file`、`attachments`、`tags`等を含む。作者の表示名はprofileの`name`から得られる。
- FANBOXサンプルはタグが`null`。Patreonサンプルには`{comics,flambert,wip}`という**配列形式を表す文字列**があり、HTMLにも対応する3タグのリンクがあった。タグを単純にJSON配列と仮定しない。
- 投稿APIには公開資料に記載されていない追加項目もある。サンプルの`origin`はURLではなく`import`だった。元投稿URLの項目として誤用しない。
- `/fanbox/post/{id}`、`/patreon/post/{id}`の短いURLは、今回のサンプルでは作者IDを含む通常投稿URLへリダイレクトした。
- FANBOX投稿の`og:image`は**作者アイコン**だった。表紙には採用しない。

サイト全体のタグ形式・原投稿の削除状況・全件性は、この少数サンプルだけでは保証できない。

## メタデータの取り込み案（未確定）

| Folio項目 | 提案 |
|---|---|
| タイトル | 投稿の`title`をそのまま使用。作者名等を追加しない |
| 作者 | profileの`name`。取得できなければ空欄＋警告。数値IDを作者名にしない |
| 表紙 | `file`が静止画像ならそれを優先し、なければ`attachments`の先頭の静止画像を使用 |
| タグ | その投稿のタグのみ。ない場合は空欄。属性処理はnhentaiと同じ未指定／既存属性選択の仕組みを使う |
| 主リンク | 正規化したPawchiveの投稿URL、ラベル`Pawchive` |
| 副リンク | 対応するFANBOX／Patreon元投稿へのURL。作者トップページで代用しない |
| その他 | サークル・シリーズ・キャラクター・言語・ページ数を本文から推測しない。漫画以外の投稿もあるのでカテゴリを一律に漫画へ設定しない |

タグの文字列形式には引用符やエスケープを含む場合が考えられる。単純なカンマ分割を避け、実装時に配列／文字列／nullを扱い、読めない形式では警告してメタデータ全体の失敗にしない。

## 表紙画像の方式

投稿HTMLでは、画像を次の二系統で表示していた。

- 原画像候補：`https://file.pawchive.pw/data/{path}`（HTMLのダウンロードリンクではファイル名のクエリも付く）。
- サムネイル：`https://img.pawchive.pw/thumbnail/data/{path}`。

FANBOXサンプルの両URLにGETし、レスポンスの先頭32バイトだけをメモリで読んだ。両方HTTP 200、画像Content-Type、原画像のJPEG署名を確認。画像をファイルへ保存・表示していない。原画像のContent-Lengthは約98KBだった。

サムネイルは`image/jpeg`というヘッダーに対して先頭が`RIFF`であり、拡張子・Content-Typeと実際の画像形式が一致しない可能性がある。実装時はバイト署名で形式を検査する。既存ストアアダプターの「宣言MIMEと署名の一致が必須」という処理をそのまま流用すると、このサムネイルが拒否される可能性がある。

現在と同じ、URLだけをDBに保存し、必要時にFolioサーバーが画像をRAMへ取得・中継する方式を提案。許可するホストとパスを限定し、DNS検証・サイズ上限・タイムアウト・リダイレクト先確認を行う。画像取得にPawchiveアカウントのセッションを付ける設計にはしない。ZIP・PDF・動画の中身をダウンロードして表紙を抽出する処理は初期案に含めない。

## 元投稿の副リンク

サンプルの投稿JSON・HTMLには、元投稿URLそのものは見当たらなかった。そのため以下は**取得値からURLを組み立てる提案**であり、元投稿の現在の閲覧成功を確認したものではない。

- Patreon：サービス名と投稿IDから `https://www.patreon.com/posts/{post_id}` の投稿リンクを作る案。
- FANBOX：profileに公開名`public_id`があれば `https://{public_id}.fanbox.cc/posts/{post_id}` を作る案。今回のFANBOXサンプルでは公開名が存在した。
- FANBOXの公開名がない／検証できない場合は副リンクを空欄にし、警告する。作者トップリンクを投稿リンクの代わりに登録しない。

元サイトの投稿が削除・非公開・会員限定でも、元投稿を示すリンクとして保存するかを決める必要がある。組み立てたURLのHTTP成功は元投稿へのアクセス権を保証しない。副リンクの収集目的で有料本文やファイルを取得する必要はない。

## お気に入り一括取り込み

Swaggerの認証は`cookieAuth`、Cookie名は`session`。独立したBearer APIキーや読み取り専用キーの定義はなかった。「typeがapiKey」というOpenAPI上の表現だけで、APIキー発行機能があると判断しない。

サイトには [Favorites](https://pawchive.pw/favorites) と [Keys](https://pawchive.pw/account/keys) の入口があるが、匿名アクセスはログイン画面へ移動した。Keys画面の用途・キー発行・権限は未確認。[サイトのインポート説明](https://pawchive.pw/importer/tutorial)では元サービスのセッションキーを使う別機能が説明されているため、Keysという名前だけでFolio用のAPIキーだと決めない。

お気に入りAPIは`type=post`と`type=artist`を区別する。F-020は**お気に入り投稿**を対象とし、作者の全投稿取得とは分ける。公開資料では応答例の項目が作者向けに見え、投稿の作者ID・URLの表し方が十分に説明されていない。認証済み応答の形・全件性・ページ送り・件数上限は実アカウントでの追加確認が必要。

実装案は、読み取り専用の一覧列挙→対応サービスの投稿URL作成→共通インポーター・バッチへの受け渡し。開始前の件数確認、重複スキップ、進捗、停止・再開、失敗レポートを用意する。認証情報の入力・保管・期限は取得方式を確認してから決める。認証情報をチャット・Git・作品DBへ記録しない。

## Folioへの組み込みで必要な改修

現行コードを読み、以下の接続箇所を確認した。

- `importer.py`：Pawchive URL判定、個別アダプター呼び出し、属性なしソース判定。
- `source_identity.py`：サービス・作者ID・投稿IDを使う正規化。通常URLと短いURL、クエリ付きURLの扱いを整理する。
- `cover_sources.py`：許可したPawchive画像URLを既存RAMキャッシュへ中継。
- フロントの共有・ブックマークレット・単独インポート・カードのリンクラベル判定：新しいソースを認識。
- `import_jobs.py`：現在は取得データへ主リンク一件を設定しているため、インポーターからの元投稿副リンクを維持する拡張が必要。同一作品候補へリンクだけ追加する経路でも、副リンクが失われないよう扱う。
- 元投稿リンクが既に別作品へ登録されている場合は、既存の重複・副リンク追加確認へ接続する。タイトルだけで自動統合しない。
- Favorites：現在の一覧取得はnhentai認証に結び付いているため、サイト別の認証・列挙処理に拡張が必要。既存のキーを流用しない。

Pawchiveと元サービスのURLの組を持てる一方、Folioの内部作品IDは維持する。APIの`user`はFolio利用者ではなく元サービスの作者IDとして扱う。

## 実装前に決めたい点

1. **表紙**：投稿の最初の静止画像を採用し、画像なし投稿も画像なしで登録してよいか。動画・ZIP・PDFからの抽出は初期版で行わない案。
2. **元投稿リンク**：取得値から組み立てて保存してよいか。削除・会員限定を許容し、FANBOX公開名が不明な場合は副リンクなし＋警告の案。
3. **対象投稿**：初期版はFANBOX／Patreonのみ、カテゴリ未指定を基本にしてよいか。Discord等の扱いは別仕様にする案。
4. **Favorites**：公開仕様はセッション認証。まず個別・ブックマーク・共有を実装し、Favoritesは認証済み応答と安全な接続方法を確認する段階を別に設ける案。

現段階ではAPIキーの提供依頼はしない。個別投稿取得の成功をFavorites取得の成功として扱わず、実装承認後も少数サンプルを使って元投稿URL・画像なし・タグ文字列・重複副リンクを検証する。
