# 常時稼働と公開版を見据えた運用比較

調査：2026-10-13。契約・移行・公開は未実施、未承認。価格は当日の参考値で、契約時に再確認する。

## 推奨案

個人版は国内Linux VPSで常時稼働させ、Tailscaleで個人端末だけから接続する案を第一候補とする。
現在のSQLite・Python・取込ジョブを保ち、PC停止中にも使える状態を先に作る。
共有カタログ版は同じVPS製品へ配置できるが、公開前にアプリ・認証・DBを改修する。
公開版のデータモデルが未確定の現在、先に全面的なDB移行をする必要はない。
これは費用と改修量を考慮した開発側の提案で、採用決定ではない。

## 候補比較

| 候補 | 費用の目安／性質 | 現行版の移行 | 公開カタログ向け | 主な負担 |
|---|---|---|---|---|
| さくらのVPS | 石狩1GB月880円、2GB月1,738円。年払いの月換算807円／1,594円 | 小〜中。OS・自動起動・暗号化キー保存を変更 | まず1台で開始し、DBやworkerの分離を検討できる | OS更新、監視、復元、障害対応を自分で管理 |
| Hetzner Cloud | ユーロ建て。地域・IPv4・税・バックアップで総額が変わる | Linux VPSとして同様 | 候補になるが日本からの遅延と元サイト到達を実測する必要 | 為替、リージョン、運用管理 |
| Render有料 | Web・DB・worker・ディスクを別々に見積もる | 中。SQLiteなら永続ディスク必須 | 運用負担を減らす候補。PostgreSQL＋workerと相性を評価 | サービス数に伴う費用、ディスクの配備制約 |
| Cloudflare Workers＋D1 | D1無料枠あり。ただしWorkersなどの費用と制限も別途評価 | 大。Pythonの常駐スレッド・SQLite接続・独自SQL関数をそのまま移せない | 読取中心の共有カタログ入口の候補。全面採用は試作と計測後 | 書込・集計・ジョブ・画像中継の再設計 |
| 自宅の小型PC／NAS | 機器代・電力・回線 | 小〜中。メインPCの停止は可能 | 公開サービスの初期候補には推奨しにくい | 停電・回線・バックアップ・宅内障害 |

国内VPSの料金・CPU・SSDなどは[公式料金表](https://vps.sakura.ad.jp/specification/)で確認。上記は石狩プランであり東京／大阪の料金ではない。初期移行は月払いで試す案。1GBで十分かは画像同時取得と取込中のメモリを実測し、余裕を優先するなら2GBを候補とする。公開ユーザー数に対する容量保証ではない。

海外VPSの価格改定と地域差は[Hetzner公式](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/)を参照。現在の総額を固定値として断定せず、対象地域の見積もりを取る。

Render無料Webは永続ディスクが使えず、ローカルファイルの変更は再起動等で保持されないため、現在のSQLite版をそのまま本番移行しない。[無料枠](https://render.com/docs/free)・[ディスク](https://render.com/docs/disks)・[料金](https://render.com/pricing)。今回料金ページから個別computeの金額を確実に読み取れなかったため、金額の比較は未完。無料Postgresにも制限があるため常用DBとして決め打ちしない。

D1無料枠は読み取った行500万／日、書込10万／日、合計5GB。検索の返却件数ではなく走査した行数で計上されるため、全ユーザーのタグ集計や検索で実測が必要。[料金](https://developers.cloudflare.com/d1/platform/pricing/)・[制限](https://developers.cloudflare.com/d1/platform/limits/)。Workers・Queues等を含む総額やCPU上限はこの数値に含まれない。

## 公開版を先取りする構成案

個人運用：スマホ／PC → Tailscale HTTPS → Linux VPS → 現行Folio＋SQLite。
公開版：ブラウザー → 公開HTTPS／リバースプロキシ → 認証付きアプリ → PostgreSQL。
取得・集計は別workerへ分離し、サイトごとのレート制限を全workerで共有する。
初期はアプリ・DB・workerを1台に同居させてもよい。成長時に分離可能な境界を用意する。
マイクロサービス化や常駐AI、Redisの採用を初期の必須条件にはしない。

Pythonを継続する場合、認証・管理画面などを持つDjangoを公開版候補とする。現行標準HTTPサーバーをそのまま一般公開する案は採用しない。フレームワークは未選定。[Django配備の確認事項](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/)。

SQLiteは小〜中規模Webでも利用できるが、同時writerは1つ。個人版には適しており、公開集計・取込・多数ユーザー更新が増える段階でPostgreSQLを推奨する判断である。[SQLiteの用途](https://www.sqlite.org/whentouse.html)。
PostgreSQLの行レベル制御は分離を補助できるが、owner権限等に例外があるので自動的に安全にはならない。アプリの認可と分離テストが必要。[公式説明](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。

## 費用に含めて考えるもの

ドメイン、別系統へのバックアップ、DB/worker、監視、メール送信、画像中継の転送量、サポート・通報対応、必要ならAI推論費用。
画像を保存しない現在の方針でも転送量・RAM・同時接続の費用は発生する。
成人向け・各ソースリンクの公開掲載・画像中継について、候補業者の利用条件を契約前に確認する。今回、各業者がこの具体的用途を許可するとは確認していない。
X等の取得方式・API費用も未確定で、常時稼働サーバーの契約だけでは解決しない。

## 移行手順案と合格条件

1. 月額上限、リージョン、個人運用の期間を決める。まず試験環境へ空DBを配備。
2. LinuxでHitomi・nhentai・momon-gaのメタデータ／RAM画像中継を実測。クラウドのIPからも取得できるか確認。
3. Windows DPAPIに依存するキー保存を置き換える。旧暗号文はコピーで使えない。キーはユーザーが再入力する。
4. SQLiteバックアップを一時環境へ復元し、全テーブル・件数・履歴・マーク・タグ属性を比較。
5. PC側の書込を止めて最終バックアップを取り、VPSへ一本化。二重運用を避ける。
6. PWAとブックマークレットの接続先を変更。端末が新originへ移るためブラウザー設定の移行も確認。
7. 再起動、取込一時停止／再開、失敗、監視、バックアップ復元を確認。PCを停止してスマホから試す。
8. 切戻しは移行後の新しいデータを含むバックアップで行い、古いPC版を単に再開しない。

OneDriveのWindows同期クライアントはLinux VPSには引き継がれない。サーバーの外部保管を別途設定する。PC停止中も届く保管先が必要で、暗号化・認証・世代保持・復元検証を設計する。利用中SQLiteファイルを同期フォルダーで共有しない。

次回の最小確認：月額上限、国内優先か、まず個人VPS版を作るか。今回サーバー契約・データ転送・公開設定は行っていない。
