# ブラウザーからの汎用取り込み — 実現性検証

2026-10-16。ユーザー依頼：開いているブラウザーのページからタイトル・表示画像を取得する方式を試し、可能な範囲を報告する。本資料は検証結果と実装案であり、本番実装の完了や仕様の確定を意味しない。

## 結果

## 試作した抽出処理

本番と独立した `media-library/test-output/browser-import-probe/` に試作を作成した。現在のライブラリ、インポーター、ブックマークレット、本番VPSを変更せず、作品登録・インポートジョブの実行も行っていない。試作はローカルの作業用ファイルであり、Gitの対象外。

- タイトルは `og:title → twitter:title → h1 → document.title`。Xでは本文を先頭180文字まで仮タイトルにする。今回はdata-testidによる本文取得対象がなく、OG説明から取得した。作品名そのものの特定・生成は行わない。
- 画像はOG画像・Twitter画像を優先し、表示済みimgから追加候補を取得。相対URLを解決し、http(s)だけを対象にする。data/blobや認証情報を含むURLは転送しない。
- DOM画像は表示サイズ80×80以上・画像実寸160×160以上を基準に取得。最大250要素から候補12件までに制限する。遅延読み込みされていない画像、CSS背景、別オリジンiframe、非公開の内部状態には今回は対応しない。
- Xでは対象投稿のarticleに範囲を絞り、プロフィール画像・返信・入れ子の引用画像を候補から除外する。媒体IDが同じlarge/small画像を重複排除した。提供例では2候補になった。
- HentaiPawとBOOK☆WALKERは12候補上限に達した。BOOK☆WALKERには広告・別巻などの画像も混ざる。画像候補一覧をすべて正しい表紙と扱ってはいけない。今回は各サイトの最初の正しい表紙1件を検証先へ渡した。
- 候補データのURLフラグメント用エンコード長は、X2052文字、HentaiPaw3554文字、BOOK☆WALKER5767文字。実測したサンプル値であり、全ページの最大値を保証しない。

## 受け渡しと画像表示の検証範囲

1. 実サイト3件では、同じ試作関数をブラウザーの読み取り専用DOM検査として実行。結果をローカルの入力欄に渡してプレビューし、先頭の表紙が読み込み完了したことを画像実寸・load件数で確認した。元サイトからFolioへ直接ブックマークレットを起動したという検証ではない。
2. 制御できるローカル元ページ（127.0.0.1:8873）では、実際のjavascriptリンクをクリックし、JSONをフラグメントに格納して別オリジンの受け取りページ（8874）へ遷移した。日本語・&・♡を含むタイトルが一致し、生成したSVG画像2件が表示され、DB保存なしを確認した。フラグメントは受け取り後にURLから除去する。
3. 同じ元ページにCSP `script-src 'self'` を設定した試験では、javascriptリンクのクリックは遷移せず、securitypolicyviolationで `script-src-elem / inline` を確認した。制限のあるページでDOMを検査できたことと、そこでブックマークレットを起動できることは区別する。実ブラウザーのブックマーク経由の扱いはブラウザーごとに確認する必要がある。
4. 上記はデスクトップのアプリ内ブラウザーでの結果。Android Chrome/Braveの実機ブックマークレットやOS共有の実際の送信内容は未検証。全サイトでの成功率を示すものではない。

検証スクリーンショットは作業用フォルダの `browser-probe-proof.jpg`。実サイトの画像はスクリーンショット・ファイルとして保存していない。保存したのは自作SVG2枚を使ったローカル検証画面だけ。

## ブックマークレットと通常の共有の違い

ブックマークレットは、ユーザーが開いているページ内で実行できれば、そのDOMのタイトル・メタ情報・画像URLを収集してFolioへ渡せる。Folioへの画面遷移で受け取る方式なら、元サイトからFolio APIへのクロスオリジンfetchは不要。

通常の「共有 → Folio」は、送信側が明示的に渡した `title`・`text`・`url` 等だけを受信する。共有先が送信元ページのDOMを読む権限は得られない。Folioの現行manifestはこの3項目をGETで受け取り、app.jsは一旦sessionStorageへ保持するが、未対応サイトの新規ドラフトではURLしか利用していない。共有タイトルを仮入力する改善余地はあるものの、画像候補を自動的に受信できるようになるわけではない。

画像ファイルの共有受信は別の仕組みとして設計可能だが、送信側が実際にファイルを共有する必要がある。通常のURL共有から、元ページの全画像を自動取得する仕組みとしては使えない。[Chrome公式のShare Target解説](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target)。

## 本実装への提案と残る確認

- ブックマークレットは任意のhttp(s)ページに対応し、URL・タイトル候補・画像候補・出典を渡す。受け取り後に登録済みURLを照合し、既存作品があれば詳細を開き、既存データを自動上書きしない。新規は候補確認から未保存編集画面へ進む。
- 既存の専用インポーターは作者・タグ等の取得に引き続き使う。ブラウザーで取得したタイトル・表紙をどちらの優先にするかは仕様決定が必要。
- URLのフラグメントに小さなJSONを渡してすぐ除去する案を優先する。件数・文字数に上限を設け、受信データを検証してテキストとして表示する。Cookieやアカウント認証情報を転送せず、外部ページ内にFolioのAPIトークンを埋め込まない。
- 通常のOS共有と手動URL入力は「受け取ったタイトル等＋サーバーからのOGP取得／専用インポーター」で補完する。PWAだけで別タブのDOMを読む方式は採れない。
- URLを取得できても、認証必須・期限付き・参照元制限のある画像は他の場所で表示できない場合がある。既存のサーバーRAM中継も元サイトのログイン状態を引き継がない。今回は3件とも通常の画像表示だけで成功したが、画像削除後の保存性はない。
- 個人ライブラリの現行画像表示はhttp(s)の直接表示に対応する。一方、公開共有スナップショットは画像を自サーバーで中継し、取得元が対応サイトに制限されている。今回の3種類の新規画像ホストについて、共有ページまで対応するには別途、中継の対応・取得制限を設計する必要がある。今回そこは変更・実接続検証していない。
- JavaScriptリンクはCSPの影響を受ける場合がある。[MDN](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/javascript)。スマホで実際にブックマークから起動する試験、画像候補確認UI、認証必須画像と失敗時の扱いを次に確認する。

結論：ブラウザー取得を主軸にした汎用取り込みは実現性がある。提供された3件では目的のタイトル・表紙を取得・別ページ表示できた。ブックマークレットを中心とし、通常共有・手動入力では取得元にアクセスする別経路を併用する構成が適する。
