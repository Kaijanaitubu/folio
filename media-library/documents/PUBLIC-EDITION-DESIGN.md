2026-10-13。実装承認済み仕様ではない。[会議記録](PUBLIC-EDITION-DISCUSSION.md)のユーザー方針を基に、以下は主に開発側の提案。新しいユーザー案は「属性を任意で付け、好きなラベルと表示色を選ぶ」。今回は文書化のみ。

## 基本構造案

個人登録・掲載先・共有作品・寄与記録・公開集計を分ける。
ユーザーは個人登録を編集し、共有作品を直接編集しない。運営の訂正・通報・取り下げは別の経路。
個人作品IDと既存リンクを保持。個人の自由タイトルと元サイトタイトル、共有代表タイトルは別に管理。
正規化URLは掲載先のキー。巻・単話・版・シリーズの関係は別に持ち、確証のない別URLは自動統合しない。
他人のカタログを保存すると、自分の個人登録と分類を作る。以後は独立編集し、取得した版と出所を記録する。
コピーしただけのタグを新しい独立した投票に数えるかは未決定。自動コピーで支持数が自己増殖しないよう、出所と明示確認を区別する案。

## 集計・公開範囲

メタデータ必須共有、評価軸・値・レビュー・マークの任意公開はユーザー方針。
公開寄与は1ユーザー／1共有作品／1正規タグで最大1件。複数リンクや個人重複登録では増やさない。
解除・ゴミ箱・復元・退会・統合／分離・公開停止をイベントとして再集計できるようにする。
公開画面は件数を基本とし、割合の分母は仕様決定後に追加。
誰が分類したかは一般公開しないが、内部には取消・不正対処用の提供元が必要。
自由タイトル・タグ・属性に個人情報が含まれる可能性がある。公開範囲の明示、報告・公開除外手段を設ける。
旧データの公開移行は一括同意・確認工程を別途決める。現在の個人DBをそのまま公衆へ出さない。

## タグ属性案

### A：任意の属性ラベル＋色（ユーザー案を中心とする推奨候補）

所有者ごとに属性ID、ラベル、色、表示順を持つ。タグは属性なしでも存在でき、性別を初期必須にしない。
例：女性、男性、技法、雰囲気、舞台、対象年齢など。ただし全てを同じ意味の分類軸として混同しない。
色は決められた安全なパレットから選ぶ初期案。任意RGBも可能だがコントラストを検証し、色だけで属性を伝えない。
属性IDはラベル変更に影響されず、削除時はタグを消すのでなく属性だけ解除する確認を出す。
初期はタグ1個に属性0〜1個。複数属性対応を先に行うかは要相談。

個人タグの同一性を「正規名＋属性ID」にするなら、現在の同名男女タグを保てる。ただし別名衝突・属性変更・統合の範囲が複雑になる。
別案は、タグ本体を名前で識別し、属性は作品に付けたタグとの関連へ付与すること。この場合「この作品のタグだけ属性変更」が自然になるが既存のタグ編集画面を改修する必要がある。
どちらを採用するか未確定。色は同一性や公開集計キーには使わない。

### B：属性は装飾専用

属性は個人の表示整理にだけ使い、共有カタログは属性を除いたタグ名で集計する。
公開統合は簡単だが、同名タグの女性／男性など意味の区別が消える。ユーザーの必須メタデータ共有希望に合うか確認が必要。

### C：名前付き分類軸と値

「性別：女性」「雰囲気：日常」「媒体：Web」のように軸と値を分ける。軸／値は任意で、値ごとに色。
複数の属性を扱いやすい反面、タグの分類と作品の分類が混ざりやすく、検索・編集UIの負担が増える。初期版には重い案。

### 個人属性と共有集計の接続

個人が付けた「女」「女性」「female」は文字だけでは確実に同義と判断できない。
個人属性に共有側の意味IDを任意対応づける案。未対応のラベルは無理に集計統合せず、原ラベルと寄与を保存。
公開メタデータの意味と個人用の色を分ける。公開ページの色はカタログ側の表示規則を用い、他人の私的配色をコピーしない。
共有用意味IDの管理は運営側で行い、ユーザーは個人設定から対応候補を選ぶ。共有項目の直接編集ではない。

### 移行・検索・インポート

旧male/femaleを意味が同じ移行用属性へ写し、neutralは属性なしへ。個人タグID・別名・参照作品は維持する。
`female:` / `male:` / `none:` は互換指定として残す案。任意属性には安定番号またはIDを使い、自由ラベルの記号・空白・重複を扱う。
評価軸のratingNと同様、attrN方式は候補。`attr1:`がタグ名を指すか作品属性を指すかは先に定義する。
新規ユーザーに性別の既定属性を強制しない。旧データ利用者には互換プリセットを移す。
サイトが示す属性はインポータープロファイルで明示対応させ、任意属性への変換は設定可能にする。
既存の「最多の性別へ合わせる」は複数分類軸へそのまま一般化しない。サイトごと・対象属性群ごとに自動推定の有無を選ぶ。

## 現行仕様が公開版で困りそうな箇所

| 現行の仕様 | 公開版での課題／対応案 |
|---|---|
| OWNER=local、共通TOKEN、ログインなし | 実ユーザー認証・セッション・作品/設定/ジョブの認可。全APIで所有者確認 |
| entitiesの性別3値 | 上記の任意属性へ移行。別名一致も属性ID／所有者を含める |
| 全所で個人作品と掲載先を同じ登録へ集約 | 共有作品と個人登録を分離。公開側の統合を個人データへ勝手に反映しない |
| 所有者内で全URLを一意管理、Trashも重複扱い | 同じURLを他ユーザーが保存できる一方、掲載先を共有。個人のURLなし作品の公開可否も決める |
| sourceチェックでリンクを走査 | ユーザー数増加時には掲載先と関係の索引へ置換 |
| 評価軸・5個のマークが個人定義 | 評価の総平均不可。公開可否とラベルのプライバシー、ラベル変更後のレビュー表示を定義 |
| サークル・性別などが固定UI | 漫画一般向け既定と追加フィールドを分離。作者は複数、役割も将来検討 |
| 外部画像URL＋RAM中継 | 任意サイトの安全なURL取得、サイト別許可、元投稿削除、転送量、追跡防止。永続保存は別途合意 |
| nhentai APIキーのプロセス共通メモリ／Windows DPAPI | ユーザー別の秘密管理。Linuxへの移行、漏洩防止、キー削除、ジョブへの結びつけ |
| 1プロセス常駐worker・プロセス内レート制御 | 公開サービスではジョブ認可、排他、停止、重複実行対策と複数worker共有の制限 |
| SQLite固有SQL・Python関数・移行スクリプト | PostgreSQL移行時に検索・索引・日時・トリガー・履歴復元を再検証 |
| 7世代の同一ディレクトリバックアップ | サービス全体復元とユーザー単位復元を区別。外部保管・暗号化・世代管理 |
| PC originを保存するlocalStorage、ハッシュURLのPWA | サーバー移行で設定やインストール情報が変わる。共有入口と公開URLを再設計 |
| Title/作者の近似で副リンク候補 | 公開カタログでは巻・話・版の関係、反証・根拠・誤統合取消が必要 |
| 30日Trash/履歴 | 退会・公開集計取消・通報・取り下げ・バックアップ保持と整合させる |

## 次回仕様会議の優先順

1. タグ本体と属性の同一性、属性0〜1か複数か。
2. 個人属性を公開側でどう集計するか。
3. URLなし作品、巻・単話・翻訳・別掲載先の識別。
4. 必須公開対象、コピーからの寄与、削除・退会時の集計。
5. 任意公開レビュー・評価・マークと投稿者表示。
6. 通報・取り下げ・成人向け分類・ソース範囲・利用条件。
7. 技術構成と移行手順。[運用比較](HOSTING-COMPARISON.md)を参照。
