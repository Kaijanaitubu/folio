# F-030：ブラウザーからのバックアップ復元

2026-10-16。ユーザーがF-030の実装を依頼。既存のバックアップダウンロードに対応する、個人用ライブラリ全体の復元を実装する。作品を既存DBへ追加・マージするデータ交換機能は今回含めない。

## 利用手順

1. 「設定・バックアップ」→「バックアップから復元」で、FolioからダウンロードしたZIP、またはSQLiteバックアップを選ぶ。
2. 「内容を確認」でアップロード・整合性検証を実行する。この段階ではライブラリに変更しない。
3. 現在とバックアップの作品・ゴミ箱・メタデータ・リンク・評価・ジョブ・共有ページの件数を比較する。
4. 全体置き換えと復元対象外の説明を確認し、`RESTORE`と入力して「置き換えて復元」を押す。
5. 完了画面では、復元前のDBもZIPでダウンロードできる。「ライブラリを開く」で再読み込みする。他の端末・タブも再読み込みしてから編集する。

画面は英語・日本語対応。ファイル選択だけでは登録・復元しない。入力が一致するまで適用ボタンを無効にし、二重送信と処理中のダイアログ閉鎖を防ぐ。キャンセル・右上×・Escで未適用の確認を閉じられる。

## 対象と形式

- 作品、全ソースリンク、作者・タグ等と別名・属性、評価軸と評価、レビュー、マークとラベル、保存した検索、ゴミ箱、履歴、インポート履歴・設定をDB全体として置き換える。
- 画像の実ファイル、APIキーの暗号化ファイル、OS・Tailscale・HTTPS設定、環境変数、端末の表示言語・テーマ等のlocalStorageは復元しない。
- 共有ページの記録は復元してもすべて無効化する。現在・過去の共有リンクを自動的に公開し直さない。必要な作品は改めて共有する。
- バックアップ内の実行中ジョブを一時停止し、処理中アイテムを未処理に戻す。ジョブの資格情報参照を消し、古い一括操作の確認トークンも破棄する。再開はインポート画面で明示的に行う。
- 生のSQLite、またはDBファイル1個だけを直下に含むZIP。`.sqlite3`・`.sqlite`・`.db`を受け付ける。フォルダ・複数ファイル・暗号化ZIPは拒否。アップロードと展開後のDBはそれぞれ256 MiB以下。
- 現在稼働しているFolioと同じテーブル・索引・トリガー定義および適用済みマイグレーション番号を持つ個人用DBが対象。同じ定義であれば、更新経路による物理的な列順の違いは許容し、列名を指定してコピーする。旧版・将来版・別アプリ・手動変更した構造は自動移行せず、互換性エラーにする。旧バックアップを利用する必要がある場合は別環境で対応版を使った移行を検討する。
- 通常の稼働中SQLiteファイルを直接コピーするのではなく、Folioのバックアップ機能で作った単体の整合したスナップショットを使う。WAL・SHMファイルの追加アップロードは受け付けない。

## 整合性と復元前退避

- ファイルはストリーミングで受信し、DB配下の非公開`restore-staging/`へランダム名で保管する。ZIPのパスを展開先として使わず、宣言サイズと実読込量を制限する。
- アップロードしたDBはimmutable/read-onlyで開く。許可する既存スキーマとの一致、SQLite整合性、外部キー、個人所有者を検証する。アップロードしたSQLを実行して本番のスキーマを作り直す処理はない。
- 確認トークンはサーバーのメモリだけに保持し15分で失効。キャンセル・期限切れの定期回収・正常完了でファイルを削除する。サーバー起動時にも残った専用一時ファイルを回収する。同時保管は2件まで。
- 確認時にDB全内容の指紋を作る。適用直前に再照合し、確認後の編集・削除・閲覧履歴変更等があれば再確認を求める。実行中インポートがある場合も適用しない。
- `maintenance.py`は通常のAPI・DBトランザクション・バックグラウンドの処理を並行の共有アクセスとして扱い、復元時だけ排他にする。開始済みの取得・書き込みが終わるのを待つ（10秒でbusyエラー）。読み取りAPI全体を恒常的に直列化しない。
- SQLiteの`BEGIN IMMEDIATE`で書き込みを予約し、その状態で別の読み取り接続から現在のDBを`restore-backups/before-restore-<ランダムID>.sqlite3`へバックアップする。退避失敗時は適用しない。退避コピーは通常の7世代削除の対象外で、サーバー上に残す。Linuxではディレクトリ0700・ファイル0600。
- 既存のテーブルへデータだけを一括で移し、全テーブル・共有無効化・ジョブ停止を一つのトランザクションで確定する。DBファイルを置き換えないので、別プロセスの共有サーバーもSQLiteの一貫した旧状態または新状態を読む。
- コピー・最終検証・コミット前の失敗はロールバックする。成功後はCSRFトークンを更新し、別端末や復元前から待っていた古い画面の更新リクエストを拒否する。復元を行った画面には新トークンを返し、退避コピーをダウンロードできる。
- 通信断では成功応答だけを受信できない可能性もあるため、画面は再読み込みと現在の内容の確認を促す。成功・失敗を未確認のまま再実行しない。

## API

すべて管理用の既存private APIのみ。`X-Library-Token`と同一Origin検証を適用し、応答は`no-store`。公開共有サーバーには復元APIを追加しない。

| API | 入力・結果 |
| --- | --- |
| `POST /api/backup/preview` | 生のZIP／SQLiteバイト列とContent-Length。現在／取込件数と15分の確認トークンを返す |
| `POST /api/backup/cancel` | `{token}`。一時保管だけを削除 |
| `POST /api/backup/restore` | `{token, confirmation: "RESTORE"}`。最終検証・退避・原子的な全体復元。結果・退避ID／場所・新CSRFトークンを返す |
| `POST /api/backup/safety-download` | `{id}`。専用フォルダにある32桁hex IDの退避コピーだけをZIPでダウンロード。任意のパスは受け付けない |

既存の`POST /api/backup/download`とCLI `python server.py --restore <SQLite>`は維持する。CLIは停止中のサーバーに対する従来の別手順であり、上記のブラウザー用確認・共有無効化等を実行するコマンドではない。

## 検証

`media-library/`を作業ディレクトリとして`python -m unittest test_backup_restore test_backup_download -v`。ZIP／SQLite往復、無変更のプレビュー、キャンセル・期限、互換性・外部キー・サイズ・パス拒否、後続変更・実行中ジョブ拒否、コピー途中失敗の全ロールバック、退避コピー同一性、別読み取り接続の一貫性、排他待機、HTTP認証／Origin／メソッド、トークン更新、退避ZIP取得を隔離DBで確認する。

Windowsの全Pythonテスト304件成功（3件スキップ）、既存Nodeスクリプト19本成功。ブラウザーで英語・日本語の選択／比較、合成データの適用、退避コピーのダウンロードを確認。390px幅で横溢れがないことを確認した。実データの復元を検証目的で実行しない。配備結果は[VERIFICATION.md](VERIFICATION.md)へ記録する。
