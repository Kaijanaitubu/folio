# URLからの汎用取り込み・専用インポーター候補の調査

調査日：2026-10-16。F-027の追加調査。依頼は、提供URLからブラウザーのDOMを使わずにタイトル・表示画像を取得できるかの検証と、専用インポーター候補の整理。本資料の案は本実装の承認・完了を意味しない。

## 結論

今回提供された13件のうち、11件でタイトル候補と対象作品に対応する画像の取得方法を確認できた。ただし「共通のOGP処理だけで11件成功」という意味ではない。Xの本文選択、とらのあなのJSON-LD、AsmHentaiの遅延画像、Getchuの画像参照元、アニメイトの転送処理に補正が必要だった。画像は表紙そのものに加え、サイトが公開するシリーズ画像・エピソードのサムネイルを含む。

残り2件は紀伊國屋の年齢確認と、ヨドバシの直接HTTP取得タイムアウト。取得不能と断定せず、現条件では未解決とする。前回の3件も比較し、HentaiPawはブラウザーでは成功・VPS直接取得は403、BOOK☆WALKERとXの前回例は直接取得でも成功した。

提案する構成は「既存の専用インポーター → 未対応URLの汎用取得 → ブラウザーから渡された候補・手動入力による補完」。ブックマークレットに画像候補がある場合は、取得元と候補を示して確認できるようにする。すべてのサイトをサーバーだけで取得する設計、またはブラウザーだけで取得する設計では、今回の例でも取りこぼしが生じる。

## 方法と確認範囲

- Windows PCと実運用先のさくらVPSから、同じ13URLを匿名のHTTP GETで取得。JavaScriptを実行せず、ログイン情報や既存ブラウザーのCookieを利用しない。
- HTMLのOG/Twitterメタ情報、公開JSON-LD、h1/title、通常・遅延読み込みのimg属性、HTMLに明示されたoEmbedを調査。作品本文や章全体をダウンロードする処理は作らない。
- 基本試験ではCookieなし・最大5リクエスト。アニメイトだけは追試で新しいメモリ内CookieJar・最大9リクエストにし、普通のリダイレクトに従った。待合室のトークンを生成・偽装する処理はない。
- ホストが公開IPだけに解決することを確認し、接続先IPを固定、各転送先も再検証。TLS証明書検証を維持。ソケット18秒・応答約22秒、HTML5MiB・画像3MiBの上限を置いた調査用処理で、並列数4・ホスト別直列化を使用した。全リクエストを通した総時間上限は別途、本実装時に必要。
- 画像URLを実際に取得し、主要候補のHTTP応答と画像形式・寸法を確認。画像データはメモリ内だけで扱い、ファイルとして保存していない。別ページのimg要素での表示まで確認した前回のDOM調査と、今回のサーバー取得成功は区別する。
- 試作と詳細結果はGit対象外の `media-library/test-output/url-import-probe/`。`probe.py`、PC/VPSのresults、`supplement.py`、`final_checks.py`、`image_checks.py`。VPS上の試作は `/tmp/folio-url-import-…-20261016…`。本番プログラム、DB、サービス設定は変更していない。

## 汎用取得の実装案

1. **対応済みサイトは既存処理を優先する。** 専用処理の失敗を一般タイトルやロゴで無条件に置き換えず、失敗理由と追加候補を示す。
2. **未対応の公開URLでは、構造化データ・OGP・HTMLを組み合わせる。** 対象ページに対応するProduct/Book/ArticleなどのJSON-LDを調べ、OG/Twitterと比較する。ページ内に複数あるJSON-LDやimgを無条件に採用しない。タイトルはh1やdocument.titleでも補完する。[OGP](https://ogp.me/)、[schema.org Book](https://schema.org/Book)。
3. **画像は複数候補と取得元を提示する。** 共通ロゴ、広告、プロフィール、別商品を除外し、遅延画像属性・相対URLを扱う。画像のHTTP成功だけでは作品に合った表紙と断定しない。サーバー取得と、個人画面・公開共有画面での表示確認も分ける。
4. **ブラウザー候補を補完として受け取る。** サーバーが403、年齢確認、ログイン、JSだけのページに当たった場合、ユーザーが実際に表示しているページのタイトル・画像候補を利用する。通常のOS共有はDOMを渡さないため、URLしかない場合は入力補助と明確な失敗案内を出す。[前回の検証](BROWSER-CAPTURE-IMPORT-INVESTIGATION.md)。
5. **短い期限内に成功・失敗を返す。** 全体の取得時間、転送回数、レスポンスサイズ、画像候補数に上限を設ける。アニメイトのような正規の転送列と本当のループを区別する。待合室・認証の回避機構は作らない。
6. **通常URLを壊さない。** product_id、エピソードID等を含むクエリは保持する。DLsite/FANZA向けに確定済みのクエリ除去を他サイトへ一律適用しない。canonicalも無条件に作品識別へ採用せず、別巻・別話の集約を確認する。
7. **既存の登録・統合ルールを通す。** 登録済みの正規化URLは既存詳細へ、新規は未保存編集画面へ進む。取得だけで保存・統合・既存メタデータ上書きをしない。画像自体は永続保存せず、必要な中継はRAM内で行う。

外部URLを受け取る実装では、既存の取得処理にある公開IP限定・DNS接続先固定・転送先再検証・TLS検証・時間／サイズ制限を維持する。Cookieはブラウザーから移送せず、必要なら一回の匿名取得内だけで扱う。本実装では待合室応答に含まれる一時トークンも通常ログや公開レポートに載せない。

画像中継を任意URLの無制限プロキシとして公開しない。個人画面と共有スナップショットは現在の表示経路が異なり、新サイトの画像ホスト・参照元・応答形式の対応をそれぞれ確認する。BOOK☆WALKERの例から、汎用MIMEを理由に必ず失敗とする実装も見直し余地があるが、画像実体の検証なしに任意データを配信してよいわけではない。

Getchu・アニメイト・BOOK☆WALKERは汎用のタイトル・表紙取り込みを先に対応し、必要なら作者などを分離する専用処理を足す案。現段階では、今回の取得成功を理由に全ショップ向けの完全なメタデータインポーターが完成したとは扱わない。

## 公開版に向けたソース分類の案

ユーザーは、非公式再掲載サイトにも個人用の取得対応を行い、公開版ではソースを識別できるようにする案を示した。インポーターの有無とは別に、ドメイン単位の管理リストを持つ案が適する。

- 公式販売店、出版社／公式配信、投稿プラットフォーム、既知の非公式再掲載、未分類などを**リンクごと**に持つ。Hitomi・nhentai・momon-ga・Pawchive・HentaiPaw・AsmHentaiなどの扱いを管理リストで明示する。分類は運営が見直せるようにする。
- 年齢区分とソース種別は別項目にする。成人向けであることを非公式の判定根拠にしない。
- 同じ作品に正規販売先と非公式再掲載先が両方ある場合は、各リンクの分類を保持する。作品全体を一括で非公式と判定しない。
- 任意ドメインの適法性をAIやメタデータの文言だけで自動断定する機能にはしない。公式配信の対応ドメイン、運営への確認・修正経路を用意する。
- 公開カタログで非公式リンクを出すか、抑制・除外するか、個人データをどこまで共有するかは未決定。今回の調査で公開方針や既存個人データの削除を決めない。

## 次に仕様決定する項目

まずは「未対応URLでタイトル・表示画像の候補を出し、未保存編集画面へ進む」範囲をF-027として確定する。Xの本文タイトル、画像候補の選択、サーバー取得とブラウザー取得の優先順位、取得失敗時の案内、RAM画像中継の対象範囲を決める。その後、利用頻度の高い専用インポーターを追加する。

今回の実施は調査まで。本番へのデプロイ、作品登録、既存DB更新は行っていない。
