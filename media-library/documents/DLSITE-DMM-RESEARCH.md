## DLsiteの取得案

PC版の商品名はh1#work_name。og:titleにはサークル名やサイト名、スマホ版では割引表示も入るため、そのままタイトルに使わない。work_outlineの作者・シリーズ名・ジャンル等と、別のサークル欄を対象にする。おすすめ商品やレビューを作品のメタデータに混ぜない。

- 商品名 → title（日本語表記と巻数・副題を維持）
- 作者 → author、サークル → circle（両者を勝手に同一視しない）
- 明示シリーズ名 → series。タイトルから巻数を削った推測はしない
- ジャンル → tag。属性情報がないのでnhentai／momon-gaと同じ未指定・最多属性方式を候補にする
- 同人漫画の作品形式 → doujinshi。ゲーム／ASMR等の対応は今回の漫画インポーターの範囲とは別途決める
- 表紙 → og:imageの主画像URL。本文1ページ目やサンプルではなく販売ページの表紙
- ページ数・言語 → 明示され取得できるときだけ。今回の漫画のwork_outlineには独立したページ数欄がなかった。PDF同梱や画像サンプル数から推定しない
- キャラクター・原作／パロディ → 今回のサンプルでは対応を確定できていない。欄がない場合は空にする

PC版と-touch版は構造が異なる。スマホURLを受け取り、同じ商品IDのPC版を取得する案が簡潔。今回RJ344793でPC版とスマホ版の同一商品・同一表紙を確認できた。
RJ＋6桁・8桁の双方を実確認。BJ/VJ、商業書籍や海外／翻訳版、販売終了商品は未検証。商品IDを推測で固定桁に制限しない。

一般ユーザー向けの公式API仕様・利用条件・取得レートの保証は今回確認できていない。非公式APIサービスを導入せず、今回成功したHTML方式を第一候補とする。大量取込は直列・待機・バックオフが必要。

## DMMブックス一般向けの取得案

商品ページはJavaScriptを実行せず取得でき、Product／BookのJSON-LDとサーバー生成の作品詳細欄を含む。title・author・genre・publisher・表紙URLは構造化データ、シリーズ・ページ数等は当該商品の詳細欄から補完する案。おすすめ欄や他巻の情報を混ぜない。

確認した1冊目では作者、ジャンル、シリーズ、出版社、掲載誌／レーベル、162ページが公開されていた。2冊目は同じseriesId=816036、異なるcontentIdとタイトル・表紙だった。シリーズIDだけで重複判定すると別巻を潰すので避ける。

- タイトル・作者 → title／author。原作・作画の役割分離は現在のauthorでは失われるため、初期案は名前を複数保持
- ジャンル → 属性なしタグ、シリーズ → series、商業漫画 → manga
- 出版社・レーベル → 現在のFolioには専用欄がない。circleへ自動流用しない。初期は未取得にするか、接頭辞付きタグにするか相談
- ページ数 → 作品詳細の明示値。APIのvolumeは用途ごとに意味が違う可能性があるため、無条件にページ数へ変換しない
- ISBN・商品ID・発売日 → 将来の来歴／商品情報として有用だが、今回の初期案で新規欄を作るかは未決定
- 表紙 → og:imageの大きい画像（検証例はpl.jpg）。JSON-LDは小さいps.jpgを示したため、取得優先順位が必要

販売ページURL /product/{seriesId}/{contentId}/ を最初の対応対象にする案。試し読みURLも同じ商品パスを含むが、読書位置は販売ページの商品識別とは別。旧URL、短縮／アフィリエイトURL、latest（将来参照先が変わる）への対応は確認してから確定する。

## FANZAの取得経路と公式API

FANZA電子書籍とFANZA同人は別のサービス／ページ形式として検証する必要がある。今回、匿名リクエストは商品一覧ではなく年齢確認を返した。商品URLを使った追加検証、正規の年齢確認済み接続、公式APIのどれを採用するかは未決定。ブラウザのログインCookieやパスワードをFolioへ取り込む方式は初期案に含めない。

DMM公式ヘルプは商品データをDMM Webサービスから参照できること、およびDMM会員・アフィリエイト・API利用の登録が必要なことを説明している。[公式案内](https://support.dmm.com/affiliate/article/44077)
[API IDの発行](https://support.dmm.com/affiliate/article/47546)は利用登録後即時と説明されている。[API IDの確認](https://support.dmm.com/affiliate/article/47547)はログイン後。

[DMM側SDKの商品API資料](https://github.com/dmmlabo/dmm-go-sdk/blob/master/docs/product.md)にはapi_id・affiliate_id・siteの必須項目、service・floor・cidによる検索がある。
[商品レスポンスの型](https://github.com/dmmlabo/dmm-go-sdk/blob/master/api/product.go)にはタイトル・商品URL・大小画像URL・作者・メーカー・レーベル・シリーズ・ジャンルなどがある。ただしSDKは現在の対象フロア・全商品の収録を保証しない。FANZA同人のサークル／作者／ページ数がどの項目に入るかは実レスポンスで確認する。
[公式エラー案内](https://support.dmm.com/affiliate/article/47548)は1リクエスト100件上限と一定時間のリクエスト制限を説明している。具体的なリクエスト/分はこの資料から断定しない。

今回APIキーは取得・利用していない。API本体の応答・対象商品の収録・現行利用条件は未確認。「API方式なら確実に全件取得可能」とは判断しない。APIを採用するならIDは画面から入力し、Git／ログ／ライブラリエクスポートへ含めない設計が必要。公開カタログへの素材・データ利用条件は個人版とは別に確認する。
商品APIの文書は購入履歴やお気に入りの個人アカウントAPIを示していない。nhentai Favoritesと同じ機能まで対応できるとは判断しない。

## Folio側に必要な変更案

商品URL認識、商品IDに基づく比較キー、importer dispatcher、ブックマーク／共有／ブックマークレット対応、属性なしタグの共通ポリシー、画像ホストの限定許可とRAM中継、英日ヘルプ・サイトラベルを追加する。取得失敗を空のタイトルとして保存せず、利用者に理由を表示する。
比較キーは元URLとは別に持ち、追跡パラメータ・PC/スマホ表記差を正規化する。DLsiteは商品ID、DMMはサービスの区別＋商品IDを候補とする。シリーズIDでまとめない。翻訳／特装／単話／合本・別巻のIDは別登録。販売サイトが違うだけの同一作品は既存の候補確認・副リンク追加を使い、自動統合しない。
既存リンクの比較キー更新時に表記違いの重複が見つかる可能性があるため、既存作品を自動削除・統合しない移行が必要。
表紙はURLをDBに保持し、画像本体は今まで通り永続保存しない。今回成功した直取得だけで全環境の画像表示を保証せず、組み込み時に実ブラウザで確認する。

## 実装前に相談したい点

1. FANZAは電子書籍のみか、FANZA同人も含むか。
2. 初期は漫画・同人誌に絞るか。DLsiteのCG・ゲーム・音声を混ぜる場合はカテゴリ仕様を追加する必要がある。
3. ジャンルを既存の無属性／最多属性方式でタグ化してよいか。出版社・レーベルは省略か専用タグか。
4. 単巻／単話／特装版は別登録、シリーズはメタデータとして関連づける方針でよいか。
5. FANZAの実際の商品URLでの追加確認と、必要なら公式APIの利用登録を進めるか。秘密情報をチャットで要求しない。
6. 初期対応は個別・ブックマーク・共有・ブックマークレットとし、購入履歴／お気に入りの直接同期は別機能にするか。

すすめ方：DLsite漫画とDMMブックス一般向けのHTML取得を先に仕様化。FANZAは実商品の取得方法を確立してから同じ入口に追加する。費用・API登録・実装・本番データ登録はまだ行わない。
